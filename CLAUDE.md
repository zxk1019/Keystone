## Comandos
- `npm run dev`: abre la app en modo desarrollo (F12 abre las DevTools).
- `npm test`: tests de Vitest (`*.test.ts` junto al código) para la lógica que no necesita Electron.
- `npm run typecheck`, `npm run lint` y `npm test`: pásalos antes de dar una fase por acabada.
- `npm run build:win`: genera el instalador de Windows en `dist/keystone-<versión>-setup.exe` (con `latest.yml` y el `.blockmap`, que usan las actualizaciones) y la app sin instalar en `dist/win-unpacked/mi-estudio.exe`. No está firmado, así que SmartScreen avisa al instalarlo. Después, copia el instalador nuevo a `..\exe` (y borra el de la versión anterior si cambia el número). No sube nada a GitHub (`--publish never`): eso lo hace el workflow de Release.
- Publicar una versión: los pasos están en `CONTRIBUTING.md` (apartado «Releasing»): `CHANGELOG.md`, `npm version X.Y.Z --no-git-tag-version`, commit, y la etiqueta `vX.Y.Z` anotada. Al subir la etiqueta, `.github/workflows/release.yml` comprueba que coincide con `package.json`, compila el instalador y el APK firmado (con la clave de los secretos `ANDROID_*` del repositorio, y comprueba el certificado) y crea la Release con las notas del CHANGELOG. `.github/workflows/ci.yml` pasa en cada `push` a `main` y en cada pull request.
- `npm run icons`: vuelve a dibujar los iconos (`build/`, `resources/`, los de Android en `android/app/src/main/res/mipmap-*` y el de los avisos del móvil) a partir del dibujo de `scripts/make-icons.cjs`. La barra lateral dibuja la misma piedra en `components/KeystoneLogo.tsx`: si cambias una, cambia la otra.
- Android:
  - `npm run build:android` compila la versión móvil, la copia a `android/` y genera el APK firmado en `dist/keystone-<versión>.apk` (con `-- debug`, uno de pruebas). Después, cópialo a `..\exe`. Usa el Java 21 de Android Studio (`jbr`) solo para Gradle; el Java 17 del PC no se toca.
  - La clave de firma está en `%USERPROFILE%\.mi-estudio` (`mi-estudio-release.jks` y `keystore.properties` con la contraseña), fuera del repositorio. Sin ella no se pueden instalar actualizaciones encima de la app.
  - `npm run dev:mobile` abre la versión móvil en el navegador para ver las pantallas; los avisos no funcionan ahí.
  - Para probar el móvil virtual contra el emulador de Firebase: `VITE_FIREBASE_EMULATOR=10.0.2.2 npm run build:android -- debug` (10.0.2.2 es el PC visto desde el móvil virtual). Ese APK permite http y deja manejar la app desde las pruebas con `window.miEstudio` (como `window.api` en el PC); los que se dan al usuario se compilan sin la variable y no tienen nada de eso.
  - El móvil virtual es `Medium_Phone_API_37.0`: `emulator -avd Medium_Phone_API_37.0 -no-window -gpu swiftshader_indirect` (en `%LOCALAPPDATA%\Android\Sdk\emulator`). Arranca en hora GMT: ponlo en hora de aquí con `adb shell service call alarm 3 s16 Europe/Madrid`. Para las DevTools de la app: `adb forward tcp:9363 localabstract:webview_devtools_remote_<pid>` (el pid sale de `adb shell pidof com.miestudio.app`).
  - `electron-builder.yml` deja fuera del paquete del PC `android/` y `out/mobile`: si no, el instalador crece unos 60 MB.
- Para probar sin tocar los datos reales, lanza la app con otra carpeta de datos: `MI_ESTUDIO_DATA_DIR=<carpeta>`. Usa una ruta corta: si la ruta es larga, Windows no deja crear los archivos de Chromium y la app se cierra al arrancar. Una ejecución con esta variable cuenta como prueba (`isTestRun`) y no registra nada en Windows, ni siquiera desde `dist/win-unpacked`.
- `npm run test:emulator`: arranca el emulador de Firebase, pasa `src/shared/firebase.emulator.test.ts` (cuentas, subir y bajar, y las reglas de `firebase/firestore.rules`) y lo cierra. `npm run emulators` lo deja abierto para probar la app: lánzala con `MI_ESTUDIO_FIREBASE_EMULATOR=127.0.0.1` (solo en desarrollo; la app instalada lo ignora) y en Ajustes pon el ID de proyecto `demo-mi-estudio` y cualquier clave que empiece por `AIza` y tenga 39 caracteres.
  - El emulador usa los puertos 9099 y 8085 (el 8080 lo ocupa Oracle). Si al cerrarlo el 8085 se queda ocupado, ciérralo con `curl -X POST http://127.0.0.1:8085/shutdown`.
  - `firebase-tools` está fijado en la 14.18.0 porque las versiones nuevas piden Java 21 y en este PC hay Java 17.
  - Para probar dos dispositivos a la vez, abre dos copias con carpetas de datos distintas (`MI_ESTUDIO_DATA_DIR`).
- Para probar las actualizaciones sin GitHub:
  - PC: `MI_ESTUDIO_UPDATES_URL=http://127.0.0.1:<puerto>/` (solo en desarrollo) apunta el actualizador a una carpeta servida con `latest.yml` y el instalador de una versión mayor. Escribe `keystone-dev-app-update.yml` en la carpeta temporal y descarga en `keystone-updater-test`; bórralos al acabar. En desarrollo no se instala nada: solo se prueba hasta «lista para instalar».
  - Móvil: `VITE_UPDATES_API=http://10.0.2.2:<puerto>/latest.json npm run build:android -- debug`, con un JSON como el de la API de GitHub (`tag_name`, `assets`...). El servidor falso tiene que mandar `Access-Control-Allow-Origin: *` (la API de GitHub lo manda), si no el `fetch` falla.
- Para probar Spotify sin una cuenta real: `MI_ESTUDIO_SPOTIFY_ACCOUNTS` y `MI_ESTUDIO_SPOTIFY_API` apuntan la app a un Spotify falso. Solo funcionan en desarrollo; la app instalada los ignora.

## Dónde está cada cosa
- `src/shared/`: tipos de datos, canales IPC (`api.ts`), validación, traducciones (`locales/`) y la lógica pura. Lo usan main, el renderer y el móvil.
- `src/core/`: los servicios con estado que funcionan igual en el PC (dentro de main) y en el móvil (dentro de la app): `data/dataStore.ts` (el JSON de datos; lee y escribe a través de `TextFile`), los repos (`agendaRepos.ts`, `settingsRepo.ts`), `sync/service.ts`, `studyTimer.ts` y los textos de los avisos. No pueden importar Node ni Electron.
- `src/main/`: lo que solo es del PC: ventana, bandeja, avisos de Windows, 20-20-20, Spotify, exportar e importar con diálogos (`data/backup.ts`) y el archivo en disco (`data/nodeTextFile.ts`).
- `src/renderer/src/platform/`: `index.ts` define `Platform` y las `capabilities` (lo que el dispositivo puede hacer; las pantallas esconden el resto). La compilación elige la versión con el alias `@platform`: `desktop.ts` (el puente de Electron) o `mobile/` (Capacitor: datos en `files.ts`, avisos en `notifications.ts`, copias en `backup.ts`).
- Android: `capacitor.config.ts`, `vite.mobile.config.ts` (añade a la CSP las direcciones de Firebase) y el proyecto en `android/` (icono, `launch_screen.xml`, el icono de los avisos `ic_stat_mi_estudio.xml`, el permiso `USE_EXACT_ALARM` y la versión, que sale de `package.json`).
- Avisos en el móvil: Android no deja la app abierta, así que `planAhead` (en `src/shared/notifications.ts`, con tests) calcula los avisos de los próximos 7 días con las mismas reglas que el PC y `platform/mobile/notifications.ts` se los da al sistema. Se reprograman tras cada cambio, sincronización o al abrir la app. El botón «Hecho» y el clic llegan por `localNotificationActionPerformed`.
- Pantallas en el móvil: por debajo de `md` la barra lateral pasa a `components/BottomNav.tsx`, las páginas tienen menos margen y la semana de la agenda se desplaza de lado (empezando en hoy). `.safe-area` y `.safe-bottom` (en `main.css`) dejan sitio a las barras de Android. El botón «atrás» (`hooks/useBackButton.ts`) cierra el diálogo abierto o vuelve a Hoy.
- `src/shared/schedule.ts`: horas y solapes del horario, y la clase actual y la siguiente. Los repos de main lo usan para no guardar clases solapadas.
- `src/shared/items.ts`: qué va con retraso (solo deberes y trabajos; los exámenes y eventos pasados no), qué vence hoy o mañana y los próximos exámenes.
- Temporizador de estudio: la lógica pura está en `src/shared/studyTimer.ts` (con tests) y el servicio en `src/core/studyTimer.ts`. En el PC vive en main, porque Chromium frena los relojes de las ventanas escondidas; en el móvil, la app llama a `catchUp` al volver al frente y programa un aviso para el final del bloque mientras está en segundo plano. La pantalla recibe el estado por IPC (`onStudyState`) y la campanita suena con `onStudyPhase` (`lib/chime.ts`, Web Audio, sin archivos de sonido). Mientras se estudia, `planNotifications` recibe `studying = true` y no envía nada.
  - Modos: `studyPlan` (en `studyTimer.ts`) da los tiempos del modo elegido: «Con ordenador» (20-20-20: 20 min y 20 s), «Sin ordenador» (45 + 5) o «Personalizado» (`settings.study`, que se sincroniza). El modo (`settings.studyMode`) es de cada dispositivo y no se sincroniza; mientras es `null` vale `DEVICE_STUDY_MODE` (el PC «Con ordenador», el móvil «Sin ordenador»). Se elige encima del temporizador (`features/study/StudyModePicker.tsx`) y solo con él parado.
  - En el 20-20-20 (`eyeRest` en el estado del temporizador) el bloque siguiente empieza solo tras los 20 s, Spotify no se pausa, solo avisa el inicio del descanso y no sale la pantalla oscura del 20-20-20 mientras el temporizador está en marcha. Tras una suspensión larga, `advance` solo devuelve el último cambio (una campanita, no decenas).
- 20-20-20: la lógica pura está en `src/shared/eyeBreak.ts` (con tests): suma el tiempo de uso, lo reinicia por inactividad o en un descanso de estudio, y gestiona las pausas. `src/main/eyeBreak.ts` la ejecuta cada 10 s y abre una ventana oscura por monitor, que carga la misma app React con `#eye-break` (`features/eyeBreak/EyeBreakOverlay.tsx`). `src/main/fullscreen.ts` pregunta a Windows con PowerShell (`SHQueryUserNotificationState`) si hay un juego o una presentación a pantalla completa; si la hay, lo intenta a los 2 min.
- Spotify: la app controla el Spotify oficial con la Web API (Spotify Connect); no reproduce nada. El login es PKCE con un servidor temporal en `127.0.0.1:43821/callback`, que tiene que coincidir con la Redirect URI del panel de Spotify. Los tokens viven solo en main (`src/main/spotify/`) y la sesión se guarda cifrada con `safeStorage` en `mi-estudio-spotify.bin`, fuera de las copias de seguridad. Las respuestas de la API se leen en `src/shared/spotify.ts` (con tests), junto con la decisión de pausar o reanudar la música con el temporizador (`studyMusicAction`). El panel está en `features/study/SpotifyPanel.tsx`.
- Contenido de Estudio: las técnicas (`study.techniques.items`) están en `src/shared/locales/`. Los consejos se quitaron en la fase 11.
- Avisos: `src/shared/notifications.ts` (`planNotifications`) decide qué toca enviar. Es una función pura con tests. `src/main/notifier.ts` la ejecuta cada minuto y muestra los avisos, `src/main/notificationText.ts` escribe sus textos y `src/main/navigation.ts` lleva a la pantalla correcta al hacer clic. Lo que ya se ha enviado se guarda en `%APPDATA%\Mi Estudio\mi-estudio-avisos.json`, fuera de las copias de seguridad.
- Avisos con botón «Hecho»: en la app instalada, `src/main/toastXml.ts` escribe el aviso de Windows con enlaces `miestudio://` (`src/shared/appUrl.ts` los crea y los lee). Windows abre el enlace con la app: si ya está abierta, llega por `second-instance`; si no, por `process.argv`. `src/main/startup.ts` decide si se puede registrar algo en Windows (`mayRegister`: app instalada y no es prueba). En desarrollo los avisos son los simples (título y texto) y el clic navega con `navigation.ts`.
- Instalador: `electron-builder.yml` (NSIS de un clic, solo para el usuario, sin permisos de administrador). Al desinstalar se conservan los datos y `build/installer.nsh` borra el protocolo y el arranque con Windows.
- Sincronización: la lógica pura está en `src/shared/sync.ts` (con tests): las claves de cada registro (`items/<id>`, `settings/shared`...), qué cambió (`trackChanges`), qué subir (`pendingRecords`) y cómo aplicar lo que llega (`applyRemote`, gana el último cambio). `DataStore.update` apunta cada cambio solo; lo que llega de la nube entra con `replaceFromSync`, que no lo apunta como cambio propio. La API REST de Firebase (cuentas y Firestore) está en `src/shared/firebase.ts`, y `src/main/sync/service.ts` decide cuándo sincronizar. La sesión se guarda cifrada en `mi-estudio-sync.bin` (`secureFile.ts`, igual que la de Spotify).
  - Si añades un campo sincronizado a un registro, los dispositivos con la versión vieja lo perderán al editar ese registro. Si añades un tipo de registro nuevo, la versión vieja lo ignora (y al actualizarse tiene que volver a bajarlo todo, como hace el paso de los datos de la versión 2 a la 3).
  - Las reglas de `firebase/firestore.rules` dicen qué colecciones se aceptan (desde la fase 11, también `habits` y `habitMarks`). Si se añade otra, quien ya tenga su proyecto de Firebase tiene que pegar las reglas nuevas; la guía de Ajustes → Sincronización enseña siempre las de este archivo.
  - Las asignaturas se guardan en orden alfabético (`sortSubjects`), para que el PC y el móvil las muestren igual.
- `src/preload/index.ts`: lo único que ve el renderer del proceso main (`window.api`).
- `src/renderer/src/`: React. Las pantallas van en `features/`, el estado en `store/` (zustand), la lógica pura en `lib/` y los componentes comunes (botón, diálogo, campo) en `components/`.
- Agenda: `features/agenda/WeekGrid.tsx` es la cuadrícula semanal que usan tanto la vista como el editor del horario. Los colores de las asignaturas están en `subjectStyles.ts`.
- Tareas: `features/tasks/ItemDialog.tsx` es el único formulario de elementos. Se abre desde cualquier pantalla con `useItemDialogStore` (`openNew` / `openEdit`).
- Hábitos: la racha, el récord y qué días se pueden marcar están en `src/shared/habits.ts` (con tests); se guardan con `core/data/habitsRepo.ts` y la pantalla está en `features/habits/` (semana, mes y el diálogo). Cada día marcado es un registro propio (`habitMarks`, id `<hábitoId>/<fecha>`), así el PC y el móvil pueden marcar días distintos sin pisarse. Los días sin marcar no se guardan. El selector de colores (`components/ColorPicker.tsx`) es el mismo de las asignaturas.
- Actualizaciones: `src/shared/updates.ts` (con tests) tiene el repositorio, los estados (`UpdateStatus`), la comparación de versiones y cómo leer la última Release. En el PC, `src/main/updater.ts` envuelve `electron-updater` (solo en la app instalada y fuera de las pruebas); la configuración sale de `electron-builder.yml` (`publish`). En el móvil, `platform/mobile/index.ts` pregunta a la API de GitHub (con 20 s de límite) y abre la descarga en el navegador. La pantalla: `store/updateStore.ts`, `components/UpdateBanner.tsx` y `features/settings/UpdatesSection.tsx`. Al actualizar, `build/installer.nsh` no borra el protocolo ni el arranque con Windows (`${isUpdated}`).
- Documentos públicos: `README.md` (inglés) y `README.es.md` con las capturas de `docs/images/<en|es>/` (hechas con datos de ejemplo, nunca con los reales), `CHANGELOG.md`, `CONTRIBUTING.md`, `SECURITY.md`, `LICENSE` y `.github/` (workflows, Dependabot y plantillas). Si cambias algo que el usuario nota, apúntalo en «Unreleased» del CHANGELOG.
- `docs/ejemplo-horario.json`: un horario de ejemplo para probar. Se carga con Ajustes → Importar copia, que reemplaza los datos. El horario real del usuario (`docs/mi-horario.json`) está en `.gitignore` y no se sube nunca.
- Los datos se guardan en `%APPDATA%\Mi Estudio\mi-estudio-data.json` (versión 3 desde la fase 11, con los hábitos). Los archivos viejos se convierten solos al abrir la app y antes se guarda una copia (`mi-estudio-data.v1.json` o `.v2.json`). Una versión vieja de la app no abre los datos ni las copias de la versión 3. Las copias de seguridad exportadas no llevan el registro de la sincronización.

## Convenciones
- Háblame en castellano.
- El código (variables, funciones, archivos) va en inglés.
- Los textos de la interfaz van siempre en los archivos de `src/shared/locales/` (`es`, `en` y `zh-CN`), nunca escritos directamente en los componentes. Si falta una clave en `en` o `zh-CN`, el typecheck falla, y `locales/keys.test.ts` comprueba que cada `t('...')` del código existe. En desarrollo, una clave que falta sale como aviso en la consola.
- Todo lo que dependa de Electron va detrás de `src/renderer/src/platform/`, para poder pasar a Capacitor sin tocar la interfaz.
- Cualquier dato que llegue del renderer por IPC se valida en main antes de guardarlo.
- Los diálogos usan `components/Dialog.tsx`. El primer campo lleva `data-autofocus`, no `autoFocus`. Dale al diálogo una `key` que cambie en cada apertura, para que siempre empiece de cero.
- Los colores de los botones van en las variantes de `Button`. No los sobrescribas con `className`, porque las clases de Tailwind chocan.
